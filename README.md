# Codex Team Kit

Готовый набор для стандартизации разработки с OpenAI Codex: правила проекта,
четыре переиспользуемых навыка (skills), TypeScript-демо со строгой типизацией,
тесты, CI и методика оценки работы агента.

Проект подготовлен как портфолио.

## Быстрый старт

Понадобятся **Node.js 22 или новее** и **npm**. Выполните в папке проекта:

```sh
npm ci
node scripts/install-skills.mjs
npm run verify
npm run demo
```

Установщик копирует четыре навыка из `skills/` в `.agents/skills/` и отказывается
перезаписывать уже существующие навыки. Для установки нужен доступ на запись
в эту папку. Если среда Codex ограничивает такой доступ, выполните команду
установки в обычном терминале.

**Если вы распаковали ZIP-архив проекта**, папка `.agents/skills/` уже включена
в него — пропустите команду `node scripts/install-skills.mjs`.
После установки откройте новую сессию Codex в папке проекта.

Версии зависимостей зафиксированы в `package-lock.json`. Особенности его
восстановления без сети и ограничения проверки на других платформах описаны
в [историческом отчёте](docs/verification-initial.md).

## Что входит в проект

- `AGENTS.md` — правила планирования, реализации, тестирования, безопасности и передачи результата.
- `PLANS.md` — шаблон плана для сложных изменений; соглашение команды.
- `skills/` — исходники навыков `review-changes`, `write-tests`, `security-audit` и `verify-project`.
- `demo/` — обработка заявок с проверкой входных данных и допустимых переходов между статусами.
- `.github/workflows/ci.yml` — проверки кода, типов, тестов, сборки и детерминированных сценариев в GitHub Actions.
- `evals/` — примеры кода с дефектом и без него, сценарии и критерии оценки агента.
- `docs/` — упражнение по изменению кода, методика оценки, результаты проверок и материалы для отклика.

## Команды проекта

```sh
npm run lint       # Проверка кода с ESLint
npm run typecheck  # Проверка типов TypeScript
npm test           # Запуск тестов Vitest
npm run build      # Сборка в папку dist/
npm run eval       # Детерминированные проверки; требуется выполненная сборка
npm run verify     # Все проверки и автоматическое обновление docs/verification.md
npm run verify:report # То же самое: проверки с отчётом
npm run test:report # Тесты генератора отчёта
npm run demo       # Сборка и запуск демонстрационного примера
```

Команда `verify` останавливается при первой ошибке. Проверки, до которых
выполнение не дошло, нельзя считать пройденными.

## Как использовать навыки

Откройте Codex в папке проекта и отправьте нужный запрос:

```text
Используй $review-changes для ревью моих текущих изменений.
```

```text
Используй $write-tests, чтобы добавить регрессионные тесты для изменённого поведения.
```

```text
Используй $security-audit для проверки валидации входных данных и разрешений CI.
```

```text
Используй $verify-project: запусти все проверки и сообщи фактические результаты.
```

Результат ревью — конкретные замечания, упорядоченные по серьёзности. Для каждого
указываются файл и строка, условия возникновения ошибки, последствия и способ
исправления. Если дефекты не найдены, агент сообщает об этом и обозначает
ограничения проверки. Навыки ревью и аудита не изменяют файлы.

## Демонстрационный сценарий

Упражнение показывает, как добавить новую возможность с помощью Codex:
сначала описать ожидаемое поведение тестом, затем изменить код и проверить результат.
Полное задание находится в [docs/safe-change.md](docs/safe-change.md).

### Исходное поведение

Заявки проходят путь `open → in_progress → resolved`.
Также разрешён возврат `in_progress → open`. Из статуса `resolved` переходов нет.

**До начала упражнения все существующие тесты должны проходить.** Они проверяют
текущие правила, в том числе запрет повторного открытия завершённой заявки.
Прохождение этих тестов не означает, что новая возможность уже реализована.

### Задача

Добавьте один переход: `resolved → open`, чтобы завершённую заявку можно было
снова открыть. Остальные правила должны сохраниться: переходы
`resolved → in_progress` и `open → resolved` остаются запрещёнными.
Функция должна возвращать новый неизменяемый объект, сохраняя исходную заявку.
Новые зависимости не нужны.

### Порядок выполнения

Отправляйте запросы ниже по одному в одном чате Codex, открытом в папке проекта.
Дождитесь результата каждого этапа, прежде чем переходить к следующему.
Перед началом установите навыки по инструкции «Быстрый старт».

#### Этап 1. Проверить исходное состояние

Напишите в Codex:

```text
Прочитай AGENTS.md, docs/safe-change.md, demo/src/tickets.ts и
demo/tests/tickets.test.ts. Посмотри git status и текущие изменения.
Используй $verify-project и запусти npm run verify.
Объясни текущие правила переходов и сообщи результаты проверок.
Файлы пока не изменяй. После проверки остановись.
```

**Ожидаемый результат:** исходные тесты и остальные проверки проходят;
переход `resolved → open` ещё запрещён. Если исходные проверки не проходят,
сначала разберитесь с причиной. Если переход уже реализован, для упражнения
нужна отдельная копия исходной версии.

#### Этап 2. Написать тесты новой возможности

Напишите в Codex:

```text
Используй $write-tests для задания из docs/safe-change.md.
В demo/tests/tickets.test.ts обнови ожидание для resolved → open в матрице
переходов и добавь отдельный тест повторного открытия завершённой заявки.
Проверь, что возвращается новый неизменяемый объект, его остальные поля
сохранены, а исходная заявка не меняется. Сохрани проверки запрета переходов
resolved → in_progress и open → resolved.
Меняй только тесты, реализацию пока не трогай. Выполни проверки, предусмотренные
навыком, покажи изменения и результаты, затем остановись даже при падении
тестов нового поведения.
```

**Ожидаемый результат:** добавлены тесты нового поведения. При их запуске
проверки повторного открытия падают на старой реализации — на этом этапе
это ожидаемо. Codex не должен сразу менять код приложения, чтобы их исправить.

#### Этап 3. Убедиться, что тесты падают по нужной причине

Напишите в Codex:

```text
Не изменяй файлы. Проверь результат последнего npm test после добавления тестов.
Если этот запуск ещё не выполнен или результаты недоступны, запусти npm test.
Перечисли упавшие тесты и объясни причину каждого падения.
Подтверди, что проверки повторного открытия падают именно из-за запрета
resolved → open, а остальные тесты проходят. Ошибки установки зависимостей,
импорта и синтаксиса отдели от ожидаемого падения проверок поведения.
После отчёта остановись, реализацию пока не исправляй.
```

**Ожидаемый результат:** подтверждено, что новые ожидания выявляют отсутствие
нужного перехода. Если тесты падают из-за ошибки окружения или самого теста,
устраните эту проблему перед реализацией функции.

#### Этап 4. Реализовать повторное открытие

Напишите в Codex:

```text
Теперь выполни изменение из docs/safe-change.md: разреши ровно один новый
переход resolved → open в demo/src/tickets.ts.
Сохрани остальные переходы, запреты и возврат нового неизменяемого объекта.
Не ослабляй тесты и не добавляй зависимости.
Запусти npm test и npm run typecheck. Покажи diff и фактические результаты.
После этого остановись.
```

**Ожидаемый результат:** повторное открытие работает, все тесты проходят,
проверка типов завершается успешно.

#### Этап 5. Выполнить полную проверку и ревью

Напишите в Codex:

```text
Используй $verify-project для полной проверки проекта.
Затем используй $review-changes для ревью текущего diff и $security-audit
для проверки безопасности изменения.
Проверь, что добавлен только переход resolved → open, запрещённые переходы
остались запрещёнными, исходная заявка не меняется, а тесты проверяют это.
Сообщи выполненные команды, их результаты и замечания с файлами и строками.
На этом этапе файлы не изменяй, коммит не создавай и ничего не публикуй.
```

**Ожидаемый результат:** `npm run verify` проходит, результаты ревью и аудита
понятны. Самостоятельно просмотрите diff. Если есть замечания, поручите их
исправить и повторите нужные проверки перед публикацией.

#### Этап 6. Создать pull request и проверить CI

Этот запрос разрешает Codex создать коммит, отправить ветку на GitHub
и открыть pull request. Отправляйте его, когда проверили изменения и готовы
их опубликовать.

Напишите в Codex:

```text
Подготовь pull request с выполненным заданием docs/safe-change.md.
Проверь git status и адрес origin. Создай ветку feat/reopen-ticket;
если она уже существует, проверь, относится ли она к этой задаче.
Добавь в коммит только изменения этого задания, сохрани постороннюю работу.
Создай коммит, отправь ветку в origin и открой pull request в main.
В описании укажи новое поведение, тесты и фактические результаты проверок.
Проверь запуск GitHub Actions и сообщи его статус со ссылкой на PR.
Если доступ к GitHub или запуск CI недоступен, явно сообщи об этом.
Pull request не сливай.
```

**Ожидаемый результат:** создан pull request, а результат CI подтверждён
реальным запуском GitHub Actions. Локальные успешные проверки не заменяют
проверку CI.

**Последовательность упражнения:** исходные тесты проходят → тесты новой
возможности падают на старом коде → после реализации все тесты проходят.
Сам по себе повторный запуск `npm test` без изменения тестов не должен
приводить к падению.

### Что демонстрирует приложение

Некорректные входные данные и запрещённые переходы вызывают ошибки класса
`TicketError`. Изменение статуса возвращает новый объект, не меняя исходный.
Данные существуют только в памяти во время выполнения программы.
В демо нет базы данных, авторизации и HTTP-сервера: оно показывает бизнес-логику
и процесс разработки с агентом.

## Проверка результатов и ограничения

При каждом запуске `npm run verify` (или `npm run verify:report`) автоматически
обновляется [docs/verification.md](docs/verification.md): дата в UTC, Git-коммит,
наличие незакоммиченных изменений на старте, среда, команды, коды завершения
и количество тестов приложения. После первой ошибки следующие команды
помечаются как невыполненные; команда завершается с ненулевым кодом.
Отчёт отражает только последний запуск, а не обновляется при каждом изменении кода.
Сам файл отчёта исключён из определения незакоммиченных изменений.
Подробные ошибки остаются в терминале; сырой вывод не включается в Markdown.
Первоначальный отчёт сохранён в [docs/verification-initial.md](docs/verification-initial.md).

Включённая конфигурация CI
сама по себе не подтверждает успешный запуск GitHub Actions.

Команда `npm run eval` проверяет контракты приложения и структуру файлов навыков.
Она **не оценивает качество работы AI** и не доказывает, что Codex загрузил
навык и выполнил его инструкции.

Порядок независимого запуска агента, сохранения трасс и оценки результатов
описан в [docs/evaluation.md](docs/evaluation.md). Для проверки используются
как пример с известным дефектом, так и корректный код — это позволяет учитывать
ложные замечания. Без измерений проект не заявляет прирост производительности,
экономию времени или точность AI-ревью.

AI-ревью дополняет автоматические тесты и решения человека по архитектуре
и продуктовому поведению.

## Перенос в другой репозиторий

Скопируйте `AGENTS.md` и нужные каталоги навыков в `.agents/skills/` целевого
репозитория. Адаптируйте команды проверки и требования к его бизнес-логике,
затем проверьте навыки на примерах с ошибками и без них.

Сохраняйте соглашения целевого проекта. Правила обработки заявок из этого демо
не нужно переносить в несвязанные проекты. Инструкции навыков должны оставаться
короткими и соответствовать конкретным задачам.
